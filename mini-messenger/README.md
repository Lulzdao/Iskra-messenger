# Искра — сервер

Сервер корпоративного мессенджера: Node.js + WebSocket + SQLite, работает на своём железе, наружу
ничего не отправляет. Сотрудники общаются через десктоп-клиент (папка [`../desktop-client/`](../desktop-client/README-desktop-client.md)),
а веб-страница самого сервера — это **панель администратора**, а не чат. Заходить в неё через
браузер сотрудникам не нужно и не получится: без права «Админка» она сразу говорит об этом.

## Первый запуск

Рабочий сервер — **Windows Server 2016, Node.js 22**. Ставится и запускается там же, где лежит
папка проекта:

```bat
npm install
copy bootstrap-admin.example.js bootstrap-admin.js   :: впишите логин и пароль первого администратора
npm start
```

(на Linux то же самое, только `cp` вместо `copy`.)

Всё остальное создастся само: база `messenger.db`, папки `uploads/` (присланные файлы) и `logs/`.

Дальше откройте `http://адрес-сервера:3000`, войдите под учёткой из `bootstrap-admin.js`, заведите
через панель настоящих администраторов — и стартовую учётку удалите. Файл `bootstrap-admin.js`
можно оставить на диске: пока в системе есть хотя бы один администратор, он больше ничего не
создаёт. Публиковать этот файл нельзя — в нём открытым текстом лежит пароль (в `.gitignore` он уже
внесён).

Порт меняется переменной `PORT`.

## Что сделать сразу после установки

1. **Выключите самостоятельную регистрацию** — панель → «Пользователи» → верхний блок. Пока она
   включена, любой, кто дотянулся до адреса сервера, заводит себе учётку и попадает в список
   сотрудников и в общую комнату. Учётки надёжнее раздавать вручную.
2. **Настройте резервное копирование `messenger.db`** — это вся переписка организации. Копировать
   лучше при остановленном сервере либо командой `sqlite3 messenger.db ".backup копия.db"`: простое
   копирование файла на работающей базе может дать битую копию (включён режим WAL).
3. **Держите процесс под присмотром**, чтобы сервер поднимался после перезагрузки машины сам.
   На Windows Server — служба (`nssm`, `node-windows`) либо задание в планировщике с триггером «при
   запуске системы»; запуск через открытое окно консоли не годится: оно закроется вместе с сеансом.
   На Linux — `pm2` или systemd.

## Ключ подписи токенов

Задавать вручную не требуется: при первом запуске сервер сам сгенерирует случайный ключ и сохранит
его в базу. Если ключ хранится у вас централизованно — можно задать своим: `JWT_SECRET=...`, он
имеет приоритет.

> **Обновляетесь с версии до августа 2026?** Раньше при незаданном `JWT_SECRET` использовалась
> строка-заглушка из открытого кода — то есть ключ подписи был публично известен, и зная его, можно
> было войти под кем угодно, включая администратора, вообще не зная паролей. Теперь ключ свой.
> Из-за смены ключа всем один раз придётся заново войти в клиент — это ожидаемо и происходит однократно.

## Панель администратора

| Раздел | Что в нём |
|---|---|
| **Обзор** | Сколько сотрудников, сколько сейчас в сети, отделов, сообщений, сколько работает сервер |
| **Пользователи** | Выключатель самостоятельной регистрации; отделы (создать, переименовать, порядок стрелками ↑↓); сотрудники — завести, сменить отдел, имя или пароль, выдать права, удалить; поиск |
| **Переписки** | Просмотр истории любого чата с подгрузкой более ранних сообщений и выгрузкой в `.txt` |
| **Рассылка** | Отправить объявление всем + лента прошлых |
| **Файлы** | Всё, что когда-либо присылали: кто, куда, когда, сколько весит; удаление с диска; здесь же — разрешённые типы файлов и максимальный размер |
| **Клиенты** | Какие версии выложены на сервере; кто сейчас в сети, с какой версией и сборкой; запуск обновления на конкретной машине; запрос журнала с неё |
| **Логи** | События сервера и ошибки с рабочих мест сотрудников за выбранный день, с фильтром по важности |

## Обновления клиента

Сервер заодно раздаёт обновления десктоп-клиента — отдельная инфраструктура не нужна. Файлы кладут
в папки рядом с `server.js`, по одной на каждую сборку:

```
updates/win7/    установщик и latest.yml для Windows 7 и 8.1
updates/win10/   то же для Windows 10 и новее
```

Раскладывать **строго раздельно**: сборки несут разные версии Electron, и клиент, скачавший чужое
обновление, перестанет запускаться. Перезапускать сервер после выкладки не нужно.

Как собирать и выпускать — см. [README клиента](../desktop-client/README-desktop-client.md).

Раздел **«Клиенты»** в панели показывает, что выложено и кто на какой версии сидит. Там же:

- **«Обновить»** — запускает обновление на конкретной машине, не дожидаясь, пока сотрудник выйдет
  из приложения. У него появится предупреждение, через 15 секунд приложение перезапустится.
  Кнопка доступна, только если версия на машине действительно отстаёт от выложенной.
- **«Журнал»** — запрашивает с машины её локальный файл ошибок. Туда попадает то, чего нет в общих
  логах: падения окон и сбои обновления — то есть ровно те случаи, когда окно уже не может ничего
  сообщить само. Раньше добраться до этого файла можно было, только придя к человеку за компьютер.

Ошибки главного процесса клиента (включая сбои обновления) теперь и сами доходят до раздела
«Логи» — искать их отдельно не нужно.

## Права

Два независимых флага, выдаются **только персонально**, каждому человеку отдельно:

- **Рассылки** — может отправить объявление всей организации;
- **Админка** — доступ к веб-панели.

Отделы на права не влияют вообще — они нужны только чтобы группировать людей в списке контактов.
Права перечитываются из базы на каждый запрос, поэтому изменение действует сразу, без перезахода.

Управление группами устроено отдельно: переименовать группу, менять её состав и удалить может тот,
кто её создал, либо администратор. Обычный участник может писать в группу и выйти из неё сам.

## Файлы

По умолчанию: не больше **50 МБ** на файл, запрещены расширения, которые Windows запускает двойным
кликом (`exe`, `bat`, `cmd`, `scr`, `msi`, `ps1`, `vbs`, `js`, `lnk`, `jar` и подобные). И список, и
режим («запрещённые» или наоборот «только разрешённые»), и размер меняются в панели без перезапуска
сервера. Жёсткий потолок, выше которого размер поднять нельзя, — 1 ГБ.

Ссылка на скачивание действует одну минуту и привязана к конкретному файлу: постоянный токен в
адресе оседал бы в логах прокси, и утечка такого лога равнялась бы утечке пароля.

Удаление файла из панели убирает его с диска, но **не трогает переписку** — сообщение остаётся, а на
его месте клиент показывает «файл удалён с сервера».

## Защита от подбора паролей

- не больше 30 попыток входа с одного адреса за 10 минут и 10 регистраций за час;
- 5 неверных паролей подряд к одному логину — логин блокируется на 5 минут, независимо от того, с
  какого адреса идёт подбор.

Все срабатывания видны в разделе «Логи».

## Шифрование канала (HTTPS)

Сервер сам разворачивает TLS — обратного прокси перед ним нет намеренно: так не остаётся
параллельного незашифрованного порта, про который легко забыть, не нужно отдельно пробрасывать
WebSocket, и `req.ip` остаётся настоящим адресом сотрудника (от него зависит защита от подбора
пароля).

Шифрование включается само, как только задан сертификат — отдельного переключателя нет, чтобы не
было состояния «сертификат положили, а включить забыли». Ничего не задано — сервер работает по
`http` и пишет в лог предупреждение `tls_disabled`. Годится для разработки, но не для рабочей сети.

### Вариант 1: PFX, как выдаёт удостоверяющий центр домена (наш случай)

Файл `.pfx` (он же `.p12`) — это сертификат и закрытый ключ в одной коробке под паролем. Именно в
таком виде его отдаёт оснастка Windows при экспорте. **Конвертировать ничего не нужно** — Node
читает этот формат сам:

```bat
set TLS_PFX=C:\iskra\p48-srv-adm01.rosstat.local.pfx
set TLS_PFX_PASSWORD=пароль-от-файла
set PORT=3000
npm start
```

Экспортировать из оснастки нужно **вместе со всеми сертификатами пути** (галочка «Include all
certificates in the certification path») — иначе сервер отдаст клиенту только свой сертификат, и
сервер об этом предупредит: `tls_chain_incomplete`.

Пароль от PFX живёт только в скрипте запуска или в переменных окружения службы. В репозитории и в
любом файле проекта ему не место — `*.pfx`, `*.key` и `*.pem` внесены в `.gitignore`.

### Вариант 2: PEM, отдельно сертификат и ключ

```bash
TLS_CERT=/etc/iskra/fullchain.crt TLS_KEY=/etc/iskra/server.key npm start
```

`TLS_CERT` — обязательно полная цепочка (`cat server.crt chain.crt > fullchain.crt`), ключ — без
пароля, иначе сервер не поднимется без ручного ввода при каждом запуске.

### Что сервер проверяет сам при старте

Сразу после запуска сервер один раз подключается сам к себе и смотрит на сертификат глазами
клиента — из PFX содержимое цепочки снаружи не видно, а в PEM легко положить лишнее. В лог попадает
строка `tls_certificate`:

```
[INFO] tls_certificate {"subject":"p48-srv-adm01.rosstat.local","san":"DNS:p48-srv-adm01.rosstat.local",
                        "issuer":"rosstat-CA-SRV-CA01-CA","valid_to":"Aug 23 11:29:43 2028 GMT",
                        "days_left":730,"certificates":2}
```

Смотреть в ней надо на две вещи:

- **`san`** — адрес в `desktop-client/config.js` должен совпадать с этим именем **дословно**. В
  нашем сертификате записано только `DNS:p48-srv-adm01.rosstat.local`, IP-адреса в нём нет: по
  `https://10.148.130.210:3000` клиент подключиться не сможет вообще, он отвергнет соединение по
  несовпадению имени. Отсюда же требование к DNS — имя должно разрешаться на всех рабочих местах.
- **`valid_to` / `days_left`** — автопродления нет, сертификат перевыпускают вручную. Наш
  действует до **23 августа 2028 года**.

Если цепочка обрывается на сертификате, который сам себя не подписывал, рядом появится
`tls_chain_incomplete`. Пропускать это предупреждение нельзя: браузеры на доменных машинах иногда
дотягивают недостающие сертификаты сами, а Node — то есть автообновление клиента — **никогда**.
Получилось бы так: в браузере всё исправно, обновления молча не идут, и причину ищут не там.

Неверный или незаданный пароль к PFX виден сразу при запуске (`tls_pfx_unreadable`), а не при первом
подключении сотрудника.

### Про порт

Порт задаётся переменной `PORT`, по умолчанию 3000. На Windows Server занять 443 можно и обычной
учёткой, но сначала проверьте, что порт свободен — если на машине стоит IIS, он держит 443 по
умолчанию:

```bat
netstat -ano | findstr :443
```

Если решите перейти на 443 — адрес в `desktop-client/config.js` меняется на
`https://p48-srv-adm01.rosstat.local` (без порта), и установщики надо пересобрать.

На Linux порт 443 требует прав root; запускать сервер под root не нужно — достаточно один раз
выдать Node право занимать привилегированные порты:
`setcap 'cap_net_bind_service=+ep' $(which node)`.

## Чего здесь нет и о чём стоит знать

- **Администратор видит любую переписку** — это осознанное свойство панели, а не упущение.
  Сквозного шифрования между собеседниками нет.
- **Кто знает техническое имя файла, тот его скачает.** Имена содержат случайную часть и попадают
  только к участникам переписки, но отдельной проверки «а вправе ли этот человек видеть этот файл»
  нет.
- **Логи хранятся вечно.** Файлы `logs/server-ГГГГ-ММ-ДД.log` и `logs/client-*.log` не чистятся
  сами — если место на диске в дефиците, настройте `logrotate` или удаляйте старые вручную.

## Обновление на существующей базе

Схема обновляется сама (недостающие колонки досоздаются при запуске), удалять `messenger.db` не
нужно и нельзя — вместе с ней удалится вся переписка.

## Нагрузка

Для 20–200 человек хватает самой скромной машины: 1 ядро, 1 ГБ памяти. Сообщения и присутствие
рассылаются по WebSocket, история отдаётся страницами по 200 сообщений.
